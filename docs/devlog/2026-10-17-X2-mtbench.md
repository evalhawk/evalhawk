# X2/X3 · MT-Bench human judgments: the first demo on real data

- **Author:** Venkata Sai Karthik
- **Date:** 2026-10-17
- **Cards:** [X2](https://github.com/evalhawk/evalhawk/issues/17), [X3](https://github.com/evalhawk/evalhawk/issues/18) · **PR:** [#28](https://github.com/evalhawk/evalhawk/pull/28)

## What I built

`experiments/datasets/mtbench_human.py`: a converter that downloads the public
[MT-Bench human judgments](https://huggingface.co/datasets/lmsys/mt_bench_human_judgments)
(CC-BY-4.0) and writes EvalHawk's recorded-outcome JSONL. Standard library only, with polite
downloading (backs off on HTTP 429) and a local cache. 13 tests, no network in tests.

## The idea, simply

In 2023 researchers showed pairs of chatbot answers to **GPT-4** and to **human experts** and
asked: *which answer is better?* That's exactly what EvalHawk needs: an AI judge's verdicts and
human verdicts on the **same** items. The job is to translate it into EvalHawk's yes/no format:

| MT-Bench | EvalHawk |
|---|---|
| "A or B better?" | Put the pair in alphabetical order; criterion: *"Is the first model's answer better?"* |
| GPT-4's verdict | the **judge** outcome |
| Each human's verdict | a **label** (several humans → majority vote) |
| Any tie | **UNKNOWN** |
| GPT-4 "tie (inconsistent)" | **UNKNOWN**: GPT-4 changed its mind when the answer order was swapped (position bias) |
| Turn 1 and 2 of one (question, pair) | one **group** (related, so same pile and wider error range) |

The fixed alphabetical order matters: about 60% of GPT-4's rows list the two models in the
opposite order from the humans' rows. Without re-ordering, they'd look like disagreements.

## The result

On 2,400 comparisons (1,814 with expert labels), the judge report card is:

| Metric | GPT-4 vs experts |
|---|---|
| Sensitivity | 0.907 [0.844, 0.946] |
| Specificity | 0.882 [0.812, 0.929] |
| Cohen's kappa | 0.790 [0.713, 0.862] |

That's about 89.5% agreement on decisive cases. The paper reports 85% for non-tie votes; ours is
a bit higher because EvalHawk takes the majority of several humans, which removes some noise.
Ties and position-inconsistent verdicts are common (about 23% of GPT-4's test verdicts), and
EvalHawk reports that rate instead of hiding it.

In the **writing** category, the naive pass rate is 50.9% but the corrected rate is about
41.5%: correcting for GPT-4's mistakes moves the answer by 9 points.

## What surprised me / gotchas

- **The overall pass rate (~50%) means nothing by itself**, because "first" is just
  alphabetical. The useful outputs are the judge report card and per-category or per-pair rates.
- **Per-pair reports are refused.** Inside one pair the outcome is nearly always the same
  (GPT-4 almost always beats GPT-3.5), so one class has too few labels. Refusing is right, but
  the message says "judge too weak", which is the wrong reason. Filed as a follow-up issue.
- The Hugging Face rows API **rate-limits** bursts (HTTP 429): the converter waits and retries,
  and caches downloads so it only happens once.
- The dataset has **no timestamps** for human votes, so every label gets one fixed, documented
  time. That keeps label IDs stable across re-imports.

## How AI helped (and where it was wrong)

Claude Code inspected the real data first (winner values, overlaps, A/B ordering), proposed the
mapping, wrote tests before code, and checked our numbers against the paper. Its first download
script ignored rate limits and failed with HTTP 429; the final version backs off and caches.
